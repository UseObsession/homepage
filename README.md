# Obsession site

useobsession.com: React 19, Vite, TypeScript and React Router, every page prerendered to its own HTML file, hosted on the free Cloudflare plan as Workers static assets. How the site is made, and every decision behind it: `docs/REBUILD.md`.

```bash
npm install
npm run dev      # http://localhost:5173
npm run build    # types, lint, share images, the client build, then every page prerendered into dist/
```

## Where things live

- **Words:** `src/content/`. Edit copy here, never in components. The contract is `src/content/types.ts`.
  - `pages/NAME.ts` exports `page` (a `Page`): Home, Agencies, Founders, Sales, Marketing, Developers. Each is served at its own `meta.path`.
  - `recipes/SLUG.ts` exports `recipe` (a `Recipe`), served at `/recipes/SLUG`. Its group, name and line feed the nav menu, the phone sheet, the footer and every recipe list.
  - `sample.ts`: the Sample output page and the output viewer (the 1 real run, the September store check).
  - `site.ts`: the Recipes index, Privacy, Agents, the 404 page and the `llms.txt` intro. `CONTROLLER` (the privacy notice's registered company name and address) is supplied by the founders before the site ships.
  - `registry.ts` finds every page and recipe file (and holds the recipes' order); `meta.ts` gives each page its title, description, share image and breadcrumb; `nav.ts`, `footer.ts`, `capture.ts` and `recipe-page.ts` hold the shared words.
  - `catalog.ts` and `heads.ts` are the index of every page the app carries without the pages' words (recipe and use case names, lines and addresses; each page's title, description and breadcrumb). They are worked out from the content at build time, and the browser gets only their values (`vite.config.ts` `contentIndex`). `words.ts` loads 1 recipe's or use case's words for its own page.
- **Design system:** `src/styles/ds/` (tokens, motion, components), synced from `Brand/Design System/` in the workspace by `node scripts/sync-assets.mjs`. Never edit it here. Site classes start `s-` and live in each component's own CSS file; `src/styles/site.css` holds the page primitives, including the 1 column split every 2 column section uses (`--s-split`).
- **App screens:** 1 React component per screen, `src/screens/NAME.tsx`, with its CSS in `src/screens/css/NAME.css` (converted from the workspace's `_research/illus/` HTML on 3 Oct 2026 by `scripts/convert-screens.mjs`; no longer synced: change them here), rendered by `components/AppScreen`. The prerender draws each page's screens into its HTML as static markup (the first view's styles written into the page, the rest loaded as each screen comes near), and writes every screen to `dist/screens/`; the browser never loads the components, and fetches a screen's HTML only when the reader moves to a page client side (`components/screens.ts`). Screens drawn for an agency take the workspace and are listed in `components/workspace.ts` (the build checks it). `npm run check:screens` proves every component still draws its original markup; `npm run screens:html -- DIR` writes every screen to its own page to look at.
- **Logo:** `components/Logo` (`Lockup`, `Mark`, `StatusMark`), files in `public/logo/` and `src/assets/logo/states/`, synced with the design system. Never retype the wordmark.
- **Partner logos:** the tools results land in (Clay, Slack, Zapier, Make, n8n; HubSpot and Salesforce ready), in 1 colour, only where the words beside them name the tool. Which logos go where is `src/content/partners.ts` (delete a line to take one off); `npm run partners` syncs the files from `Brand/Partner logos` in the workspace into `src/assets/partners/`, and only the tools that file lists. Google's and Microsoft's product icons (Gmail, Sheets, Outlook, Teams) stay out until permission is granted in full colour: both forbid recolouring them. Clay's logo needs Clay's OK before launch (press@clay.com).
- **Waitlist:** every form is `components/CaptureForm` (kinds `waitlist`, `mystery` and `verify`, the free AI agent check), sending through `src/lib/waitlist.ts` to a Google Apps Script web app (`waitlist/Code.js`) owned by jamesniranye@gmail.com. It writes each sign up to the "Sign ups" tab of the **Obsession waitlist** sheet in that Drive and emails an alert. The site reads the web app URL from `VITE_WAITLIST_URL` in `.env`. Without it the forms run in preview and send nothing.
  - **The sign up card.** The page asks for the email only and saves it at once. Then the form becomes a card in the same spot (`components/SignupSteps`), the 1 tap questions first and the typing last: "Which of these is you?" on pages that don't know their reader, 4 questions for that reader (3 for "Something else"), name and company (the company filled in from the email's domain), an optional note, then a thank you with 1 next step (the free mystery shop or AI agent check, a link to the real report, or the first company to start with). Every step can be skipped; a row of squares shows progress and takes them back to any answer. On a single choice, Next appears only once something is picked. The card's line names the email, so a typo shows early.
  - **The questions live in `src/content/signup.ts`**, with every word on the card, the first run each first job suggests, the Call first rules and the next step rules. Edit questions and options there, never in the component. A page's own question (`Capture.roles`, a recipe's) is asked in place of the first job, or in place of "Where should results land first?" when it says `replaces: 'results'` (the agencies' audit format); a free shop or check asks "Whose store/AI agent is it?" in the first job's place. A free shop or check form left blank is a plain waitlist sign up: it asks the reader's own first job and never the page's question. A page's own thank you (`Capture.done`, on a free shop or check that names a store) is the card's title and its thank you. The 5 reader pages set the reader from their address (`readers[].path`), as does the agencies use case (`page.readerOf`), each with a Change link; every other page, `/verify` included, asks "Which of these is you?" first.
  - **The card is its own chunk, and the email never waits for it.** `components/CaptureForm` (in every page that has a form) holds only the form and `lib/signupStore.ts` (the state, `sessionStorage`, step 1, the loaders), with `content/signupReaders.ts` (the readers' names and the pages that know their reader). The card (`components/SignupSteps`), its rules (`lib/signup.ts`) and the question bank (`content/signup.ts`) load on demand, warmed the moment a reader touches a form, so a page nobody signs up on carries none of them. The email is sent first; once it saves, the sign up is kept as pending and only then is the card's code asked for. If that code can't load (a deploy replaced it while the tab was open), the page reloads once and the card opens with the fresh code; if it still can't, the form says "You're on the list." The stale chunk reload in `main.tsx` runs at most once in 10 seconds. The card's styles are imported by `CaptureForm` so they keep their place in the site's 1 sheet, and `scripts/prerender.mjs` writes them into the head of every page whose code can open the card. Keep anything that reads the bank out of `CaptureForm` and `signupStore`; `content/signupFlags.ts` holds the 1 switch the privacy notice reads.
  - **One sign up, one row.** Step 1 sends the email with a random sign up ID; every later step sends the whole sign up so far with that ID, in the background (1 post in flight, the newest wins, a beacon if the page closes), stamped with the time it was made, so a slow older post never overwrites a newer one. The script finds the row by Sign up ID and checks the email and that the row is under a day old; it never updates a row by email alone. Skipped answers read "Skipped"; unreached ones stay blank. Call first reads "No" only when an answer decides it, and stays blank while its questions are skipped or unreached. The card resumes after a reload for 24 hours (`sessionStorage`).
  - **Version handshake.** The script answers every JSON post with its version (`v`). The card opens only for 2 and up; an older script keeps the email only, so the form says the plain "You're on the list." instead. The site can therefore ship before or after the script's redeploy without losing a sign up, though the card only appears once the script is redeployed.
  - Columns, in the order of a new sheet: Received, Step reached, Email, Name, Company, Reader, First job, Call first, Suggested first run, Job detail, then 1 column per reader question (Agency: clients, Founder: sells, Sales: last slip seen, and so on), Other: role, Other: did last week, Results to, Anything else, Next step, Start with, Store, Agent, Interest, Source, Page, Arrived from, Reader from, Updated, Finished, Role (old rows), Sign up ID, Sent at. Step reached reads 1 Email, 2 Reader, 3 First job, 4 Scale, 5 Results, 6 Last time, 7 Name, 8 Note, 9 Done. A value Sheets would change (a phone number typed 02079460000, a note reading 12/10) is kept as text. Columns are found by their header, so old rows are untouched; missing headers are added at the end of row 1 the first time they're needed, and can be dragged into place once. Arrived from stays empty until the founders switch on `keepArrivedFrom` in `content/signupFlags.ts` (the privacy notice follows the same switch).
  - The forms work before the page's script loads: they are real `<form method="post">` forms aimed at the same URL, and the script takes form posts as well as JSON. A form post gets a short "You're on the list" page with a link back. A post without a sign up ID still works as before (the same email and source within 10 minutes updates the same row).
  - Guards: a hidden `website` field (anything in it is treated as a bot and dropped), a formula guard on every cell, a lock around each write, at most 8 new rows per email an hour and 40 updates per sign up an hour.
  - Alerts go to every address in the script property `NOTIFY_TO` (comma separated), or to the owner when it isn't set: 1 for each new sign up (marked when the email has signed up before), 1 with every answer, the suggested first run and Call first when they finish, and 1 when they ask for a free shop or check, or name a company, from the thank you. Every address counts against the script owner's daily mail quota (100 recipients a day on a personal Google account, 1,500 on Workspace), so set `NOTIFY_TO` to 1 group address for both founders. When the quota is spent the script skips the alert and still saves the row.
  - **To change the script (James, once per change):** paste `waitlist/Code.js` into the Apps Script editor, save, then Deploy, Manage deployments, the pencil on the live deployment, Version: New version, Deploy. The URL stays the same. Opening that URL afterwards shows the live version (`"v":2`) and adds any missing column, without making a row. Click by click, with a 1 sign up test: `_research/onboarding/JAMES-REDEPLOY.md` in the workspace. **Redeploy the script before the site change ships:** the new script accepts today's forms, and until it's live the new site only shows the plain thank you (the handshake above). To send alerts to both founders, add `NOTIFY_TO` under Project Settings, Script properties.
  - After adding anything that needs a new permission, run `authorize` once from the editor and tick every box. The current version needs none beyond the first deploy's.
  - **Testing:** never post to the live web app. Build with `VITE_WAITLIST_URL` set to a local stub (a small server that logs what it receives) and `VITE_SIGNUP_TEST=1`, which turns on a test hook (`src/lib/signupTest.ts`, `?sd=4` opens step 4, `?sd=thanks` the thank you, `?sd=e2e` runs the checks on Home, `?sd=flow.agencies`, `flow.agenciesblank`, `flow.verify`, `flow.verifyblank` and `flow.recipe` run 1 page's flow, `flow.v1` checks the plain thank you against a stub running the older script, `flow.stale` the reload when the card's chunk is gone) that the site's own build never includes. Run `node waitlist/test/stub.mjs PORT DIR` for the stub (it runs the real `waitlist/Code.js` against a fake sheet), and `node waitlist/test/signup.test.mjs` and `code.test.mjs` for the unit tests.

## Build and prerender

`npm run build` runs `tsc -b`, `oxlint`, `scripts/og.mjs` (a 1200 x 630 share image per page into `public/og/`), `vite build`, then `scripts/prerender.mjs`, which:

- renders every page to its own HTML file (`dist/agencies.html`, `dist/recipes/mystery-shopper.html`) with its head: title, description, canonical, share tags, JSON-LD and font preloads, and its styles written into it (see Speed);
- writes `404.html`, `sitemap.xml`, `robots.txt`, `llms.txt` and `llms-full.txt` (every page's words as plain text);
- trims the shared stylesheet to the rules the site uses (`scripts/purge-css.mjs`), then each page's copy to the rules that page can use;
- fails the build on a broken promise: a missing share image, a JSON-LD that does not parse, a bracketed placeholder on a page, a page section missing from `llms-full.txt`, an agency screen missing from `components/workspace.ts`. Style notes (title and description lengths, links) only warn.

Code that runs while a component renders must not touch `window` or `document`; do that inside an effect.

## Speed

A page paints from its own HTML alone, and the app arrives after it:

- **No request before the first paint.** Each page carries its styles in its head (the site's, trimmed to the rules its HTML and its code can set, then the styles of the app screens its first view shows). The fonts it sets are preloaded as files. The whole site sheet stays a file for a page reached client side (`lib/siteStyles.ts`), and so do the screens' own sheets.
- **The boot script** (`src/boot.ts`, written inline at the end of every page by the prerender, never bundled) plays each app screen's story as it comes into view (a story is HTML and CSS: the `.play` class), loads each screen's styles as it comes near, and loads the app once the hero's headline and sub have landed and been painted (at once on a touch, click or key).
- **The app** is a small entry (React, the router, the nav, the footer and the index of every page) plus 1 chunk per page (`App.tsx` `lazyPage`; the page's chunk and words load before hydrating, `preloadRoute`). It hydrates in a transition, in short slices. The site's styles stay 1 sheet in their import order (`vite.config.ts` `codeSplitting`).
- **The browser skips what it can't see** (`styles/perf.css`): every app screen is a fixed 720 x 450 window drawn only near the view; hero tabs not chosen, and screens below the hero until the reader comes near, are skipped altogether.
- `styles/entrance.css` shows the hero's words from the first frame (they rise and sharpen without fading in). Delete it to bring the design system's fade back.

## Hosting

Cloudflare Workers static assets on the free plan, configured by `wrangler.jsonc`: the build command is `npm run build`, the deploy uploads `dist/`. Unknown addresses get `404.html` with a real 404. Redirects live in `public/_redirects`, response headers in `public/_headers`. Nothing may need a paid feature.

**After every deploy, ping IndexNow** (Bing and the engines that share its pings; Copilot and ChatGPT search read Bing): `npm run indexnow` sends every page in `dist/sitemap.xml`, `npm run indexnow -- /agencies /recipes/lead-leaks` only the pages that changed, `--dry-run` prints the request. It never runs on its own: run it after the deploy (for example `npx wrangler deploy && npm run indexnow`), because IndexNow checks the key file on the live site. The key is the 32 hex character file in `public/` (`scripts/indexnow.mjs` says how to replace it). The founders' side (Bing Webmaster Tools, Search Console, Cloudflare's crawler settings, Brave) is in `_research/seo/AI-SEARCH-FOUNDERS.md` in the workspace.

## Copy rules

`docs/REBUILD.md`, "Copy": numerals, British spelling, contractions, no em or en dashes, no hyphenated compounds where a plain word works, headings that make a claim, no money promises, no guarantees, no sources on the page. Every example that isn't from a real run says "Example". Run `node ~/.claude/skills/no-meta-callouts/scan.mjs dist/llms-full.txt` on the words a reader sees.
